# Security evidence by implementation

The word authenticated describes which messages are checked; it does not establish truthful behavior by a key-holding relay or production device security.

An active hop proof is an authenticated statement made by a relay. A relay holding its hop key could issue a false statement unless another mechanism constrains it. The implemented blackholes drop according to a schedule; they do not exercise every forged-proof or deceptive-telemetry strategy. A sink signature binds the declared packet identity; the sink's source-authenticator check and trusted-sink assumption supply the corresponding acceptance context.

The new antecedent audit can check a claimed proof against a logged downstream MAC outcome. A receiving router does not have the auditor's global trace access. Consequently, passing that audit is not a runtime Byzantine-forwarding guarantee. Similarly, authentication of telemetry origin does not prove its energy/queue values are truthful.

Physical boards and production protections have not become available through simulator execution. The existing board acquisition protocol, calibrated power-trace parser and production-security checklist remain evidence requirements, not certificates. No author consent, private correspondence or authenticated submission approval is inferred from code or test completion.

An ELF or source hash identifies an artifact; it does not demonstrate authenticated boot or prevent unauthorized firmware installation. No board-specific root of trust, signed-update enforcement, readout protection or rollback/reset persistence has been measured here. A compromised relay can use its own legitimate keys; authenticity of its claim is distinct from truth of the claimed forwarding event.
